"함께 보는 말씀" 카드 아키텍처

답변에 곁들이는 말씀이 어떻게 불러와지는지 — 데이터 로딩 · 주제 매칭 · 응답 합류 · 화면 표시까지
데이터(JSON) 백엔드 LLM 호출 프론트엔드
한 문장 요약 — 말씀 카드는 답변 생성과 완전히 분리된 "후처리(post-processing)"입니다. 봇이 답변을 다 만든 뒤에, ① 답변을 LLM이 주제로 분류하고 → ② 그 주제의 말씀을 featured_malssum.json에서 한 개 골라 → ③ 응답에 얹어 보내고 → ④ 화면이 카드로 그립니다. 시스템 프롬프트와는 무관합니다.

1. 핵심 개념 — "검색"이 아니라 "후처리"

흔한 오해: "말씀도 RAG로 검색해서 가져오나?" → 아닙니다. 말씀 카드는 별도의 Qdrant 컬렉션도, 임베딩도 쓰지 않습니다. 사람이 미리 추려둔 작은 JSON 목록에서 답변 주제에 맞는 것 하나를 고르는 방식입니다.

  • 데이터 소스 = backend/src/malssum/featured_malssum.json (사람이 큐레이션한 ~50개 목록)
  • 선택 기준 = "이 답변은 어떤 주제인가?"를 LLM이 분류 → 같은 주제 말씀 중 무작위
  • 관여하지 않는 것 = 봇의 시스템 프롬프트, RAG 검색 결과, 봇 종류

3. 단계별 상세 (코드 위치 포함)

1
답변 생성 — 평소 그대로

RAG 파이프라인(검색→리랭킹→생성)이 답변을 만듭니다. 말씀 로직은 여기 전혀 끼어들지 않습니다. 그래서 어떤 봇이든(집필규정 적용/미적용/RAG-only) 동일하게 동작합니다. chat/service.py · process_chat:170 / process_chat_stream:270

2
주제 분류 — LLM 1회 호출

확정된 답변 텍스트를 fast 모델에 넘겨 주제 하나를 받습니다. 분류 실패/429면 None. malssum/service.py · _classify_theme:84

async def _classify_theme(answer_text, themes):
    prompt = ("다음 답변의 핵심 주제를 아래 목록에서 하나만 골라 단어만 출력…"
              f"주제 목록: {', '.join(themes)}\n답변:\n{answer_text[:1500]}")
    raw = await generate_text(prompt)   # Gemini fast 모델
    for t in themes:
        if t in raw: return t   # 목록 단어 매칭
    return None
3
말씀 선택 — 주제 풀에서 무작위

분류된 주제로 목록을 필터링해 그 안에서 무작위 1개. 주제가 없거나 그 주제 말씀이 없으면 전체 풀 무작위로 fallback(카드는 항상 뜨도록). malssum/service.py · pick_malssum_for_answer:109

async def pick_malssum_for_answer(answer_text):
    items = _get_items()              # JSON 풀 (lazy 로드, §4)
    if not items: return None      # 풀 비면 카드 없음
    theme = await _classify_theme(answer_text, _available_themes())
    pool  = [i for i in items if i["category"] == theme] or items  # 미매칭 → 전체
    return _normalize(random.choice(pool))
4
응답 합류 — 6개 경로 모두에

동기/스트리밍 × (캐시히트/메타/본응답) = 6개 경로 각각에서 featured_malssum을 응답에 얹습니다. 본응답 경로는 지연 0으로 처리(§6).

5
화면 렌더 — 카드

프론트는 응답의 featured_malssum을 메시지에 저장하고, 본문이 있으면 카드를 그립니다. page.tsx · 877

4. 데이터는 어떻게 메모리에 올라오나 (lazy 로딩)

JSON은 서버가 처음 필요할 때 딱 1회 읽어 모듈 전역 변수 _items에 캐시합니다. 이후 모든 요청은 메모리에서 바로 씁니다 (디스크 재접근 없음).

featured_malssum.json
디스크의 큐레이션 목록. _MALSSUM_PATH:21
↓ 최초 1회 (또는 _items=None 일 때)
_load_from_disk()
JSON 파싱 + text 있는 항목만 필터. 파일 없음/깨짐 → 빈 [](카드 미표시). :27
↓
_items (모듈 전역 캐시)
_get_items(): _items is None 이면 로드, 아니면 캐시 반환. :41
↓
pick_malssum_for_answer / get_random_malssum
여기서 _items를 읽어 선택.
주의 (운영 팁) — _items는 프로세스가 살아있는 동안 캐시됩니다. JSON을 새로 채워도 서버를 재시작(또는 reload)해야 반영됩니다. uvicorn --reload는 .py만 감시하므로 JSON만 바꾸면 자동 반영되지 않습니다.

5. 6개 응답 경로 — 어디서든 동일하게

답변이 나가는 길은 6가지입니다. 각 경로가 featured_malssum을 어떻게 처리하는지:

경로위치말씀 처리
동기 · 캐시 히트service.py:202캐시된 답변으로 주제 매칭 (매 응답 fresh, 캐시엔 미저장)
동기 · 메타(거부)service.py:227None — 범위 밖/거부 답변엔 카드 없음
동기 · 본응답service.py:239asyncio.gather에 합류 → 지연 0 (§6)
SSE · 캐시 히트service.py:291위와 동일, sources 이벤트에 동봉
SSE · 메타service.py:326None
SSE · 본응답service.py:381gather 합류 → 지연 0
스트리밍은 답변 글자가 다 흐른 뒤에 sources 이벤트로 말씀이 도착합니다. 그래서 답변은 즉시 스트리밍되고, 카드만 살짝 뒤에 "톡" 뜹니다.

6. 왜 본응답은 "지연 0"인가

주제 분류는 LLM 호출(≈1초)이라 순진하게 붙이면 응답이 1초 느려집니다. 그래서 기존에 이미 병렬로 돌던 두 작업(후속질문 추천 · 마무리문구)과 같은 asyncio.gather에 끼워 동시에 돌립니다. 말씀 분류가 그 둘보다 늦지 않는 한 추가 지연은 0입니다. chat/service.py:239, 381

gathered = await asyncio.gather(
    self.suggested_followups_stage.execute(ctx),   # 기존
    self.closing_template_stage.execute(ctx),      # 기존
    pick_malssum_for_answer(ctx.answer),            # ← 끼워넣음 (병렬)
    return_exceptions=True,
)
featured = gathered[2] if isinstance(gathered[2], dict) else None

7. 데이터는 어디서 오나 — 큐레이션 파이프라인 (오프라인 1회)

featured_malssum.json은 손으로 타이핑하지 않습니다. 스크립트가 코퍼스에서 뽑고 AI가 주제를 답니다. backend/scripts/extract_malssum_candidates.py

8. JSON 한 항목의 형식

{
  "text":     "… 말씀 본문 …",        # 카드에 표시되는 본문
  "source":   "3대 경전",            # 출처 그룹 (어머님 말씀/3대 경전/자서전)
  "category": "위로",               # ← 주제(테마). 런타임 매칭의 키
  "volume":   "천성경"              # 권/출처 상세 (확장자 제거됨)
}
핵심: category 필드가 "출처"가 아니라 "주제"입니다. ②단계 분류 결과와 이 값을 맞춰 말씀을 고릅니다. 출처는 source · volume에 따로 담깁니다.
