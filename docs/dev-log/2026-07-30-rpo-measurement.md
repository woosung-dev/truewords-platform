# RPO 24시간을 실측으로 재판단한 ADR

- **작성일**: 2026-07-30
- **결정**: 백업 빈도 일 1회 → **6시간마다**. WAL 아카이빙은 **채택하지 않음**
- **관련**: [Postgres VM 이전 ADR](2026-07-29-postgres-vm-relocation-and-backup.md) · [예약 작업 조용한 실패 ADR](2026-07-30-silent-scheduled-job-failure.md)

## Context

Neon 을 떠나면서 자동 백업·PITR 을 잃었고, 일 1회 전체 덤프로 대체했다. 당시 판단은 "47MB DB 에 WAL 아카이빙은 과하고, 쓰기가 채팅 로그·설정이라 하루치 유실이 치명적이지 않다" 였다. 다만 그 판단의 근거가 **추정**이었다. 실측하고 다시 본다.

## 실측 (2026-07-30, 운영 DB)

|---|---:|---:|---:|

| `search_events` | 19 | 276 | ~20 |

### 유실 시 되살릴 다른 출처가 있는가

| 데이터 | 복구 가능성 |
|---|---|
| `session_messages` | **없다. 유일본** — 사용자 질문과 AI 답변 본문 |
| `answer_citations` | 메시지에서 파생 (메시지가 없으면 의미도 없다) |
| `search_events` | 분석용 로그. 재현 불가하나 서비스 영향 없음 |
| `chatbot_configs` | 운영자 설정. admin UI 로 재입력 가능. **14일간 변경 0건** |
| `admin_users` | 계정. 재생성 가능. **14일간 변경 0건** |

**하루치 유실의 실체는 채팅 메시지 약 43건(Q&A 21쌍)이다.** 나머지는 파생·분석·재입력 가능이다. 설정과 계정은 애초에 안 바뀐다.

### 백업 시각이 이미 최적이었다

시간대별 쓰기 분포(최근 14일, UTC)에서 **18:00~20:00 구간은 쓰기가 0** 이다. 피크는 07:00(105), 14:00(96), 13:00(60)이다. 일 1회 백업을 18:00 에 둔 것은 우연히도 가장 조용한 시각이었다.

### 저장 여유

| 항목 | 현재 | 6h 주기로 늘리면 |
|---|---|---|
| DB 크기 | 44MB | — |
| 덤프 1회 | 11MB / 1초 | 동일 |
| VM 로컬 (14일 보관) | ~154MB | ~616MB (디스크 97GB 중 19% 사용) |
| Object Storage (90일 lifecycle) | 22MB 사용 | ~4GB (Always Free **20GB**) |

## 결정

### 백업 빈도를 6시간마다로 (00/06/12/18 UTC)

RPO 24h → **6h**. 최악의 유실이 채팅 메시지 ~43건에서 ~11건으로 줄어든다.

근거는 비용 대비다. 덤프가 1초 / 11MB 라 4배로 늘려도 로컬 616MB, 원격 4GB 로 둘 다 여유 안이다. 반대로 얻는 것은 **유일본 데이터의 노출 창을 1/4로 줄이는 것**이다. 이 비대칭이면 망설일 이유가 없다.

원격 업로드도 4회 전부 한다. 처음에는 "로컬만 6h, 원격은 24h" 비대칭을 고려했는데 — 흔한 실패(DB 손상, VM 생존)와 드문 실패(VM 유실)의 복구 지점을 나누는 발상이었다 — Object Storage 여유가 충분해 굳이 두 가지 동작을 만들 이유가 없었다. **단순한 쪽이 낫다.**

### WAL 아카이빙은 채택하지 않는다

44MB DB 에서 얻는 것은 RPO 6h → 분 단위다. 대가는 세 가지다.

1. 아카이브 저장소와 보관 정책이 하나 더 생긴다.
2. 복구 절차가 base backup + 타임라인 재생으로 복잡해진다. `infra/oracle-vm/README.md` 의 복구 절이 지금은 pg_restore 한 줄이다.
3. **아카이버 자체가 또 하나의 조용한 실패 지점이 된다.** `archive_command` 가 실패하면 WAL 이 쌓여 디스크를 채우거나 아카이브에 구멍이 난다. 2026-07-24 사고가 정확히 이 부류였다 — 감시되지 않는 자동화가 조용히 죽는 것.

세 번째가 결정적이다. 이번 세션에서 조용한 실패를 잡는 데 공을 들였는데, 같은 성질의 새 실패 지점을 자발적으로 추가하는 건 앞뒤가 안 맞는다. 유일본이 하루 43건 규모인 서비스에서 감당할 복잡도가 아니다.

**재검토 조건**: `session_messages` 일평균이 500건을 넘거나, 유실이 곧 금전·법적 문제가 되는 데이터(결제, 계약 동의 기록)가 들어오는 시점.

### `ops-check.sh` 임계값 동반 수정

빈도를 바꿨으니 감시 임계도 바꿔야 한다. 그러지 않으면 26h 임계가 6h 주기의 4번 연속 실패를 통과시킨다.

- `BACKUP_MAX_AGE_H`: 26 → **8** (6h + cron 지연 여유 2h)
- `REMOTE_MAX_AGE_H`: **8** 신규 — 원격 사본 신선도를 따로 본다

## 검증

```
backup-db.sh 6h 주기 첫 실행    11M · 무결성 검증 통과 · Object Storage 업로드 완료 · 보관 4개 / 43M
crontab                          0 0,6,12,18 * * *  backup-db.sh
ops-check 전체                   불변식 6건 전부 OK · exit 0
ops-check 임계 전환 확인         전환 전(9h 경과) FAIL 2건 → 백업 1회 실행 후 OK — 임계가 실제로 작동
원인 구분 분기 A                 로컬 신선 + 원격 낡음 → "업로드가 조용히 실패"
원인 구분 분기 B                 둘 다 낡음 → "백업 자체 문제 (backup 항목 참조)"
```
