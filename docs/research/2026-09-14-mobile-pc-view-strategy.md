## 1. 결론 먼저

**B(뷰 2벌 분리)와 C(라우트 분리)는 탈락한다.** 3개 렌즈 전부에서 최하위였고, 두 안 모두 치명적 결함 판정을 받았다. 공통 사유는 하나다 — **드리프트를 감지할 신호가 이 프로젝트에 구조적으로 없다.** 기기 텔레메트리 0, 기기 관련 사용자 피드백 0건, 1인 개발 체제. 뷰가 2벌이 되는 순간 "한쪽만 고쳐지는 버그"는 *언제 시작되는가*가 아니라 *첫 레이아웃 PR부터 시작되고 영원히 감지되지 않는다*가 답이다.

**A안(반응형 단일 뷰)과 D안(PC 보류·계측 우선)이 13점 동률**이고, 이 둘은 **배타적이지 않다.** 권고는 순차 조합이다 (§5).

| 안 | 유지보수 | 실행위험 | 제품전략 | 합계 |
|---|:---:|:---:|:---:|:---:|
| **A** 반응형 단일 뷰 | 5 | 4 | 4 | **13** |
| **D** PC 보류 · 계측 우선 | 3 | 5 | 5 | **13** |
| **E** 점진적 강화 | 4 | 3 | 3 | 10 |
| B 공유훅 + 뷰 2벌 | 2 | 2 | 2 | 6 |
| C 라우트/엔트리 분리 | 1 | 1 | 1 | 3 |

## 2. 판단을 뒤집는 사실 4가지

### 2-1. "모바일 우선"은 측정된 결론이 아니라 주어진 전제다

`docs/research/2026-08-30-pwa-app-direction.md:14` 에서 이 문장은 **`### 확인 사실`** 절에 있다. 같은 문서에 근거·대안 비교·기각 사유가 없다. 승인 결정 `DEC-PWA-009`의 대립축은 **"네이티브 앱 vs 웹/PWA"**였지 "모바일 vs PC"가 아니었다. **PC 뷰를 기각한 결정은 레포 어디에도 없다.** 폼팩터·반응형을 다룬 ADR도 0건(`docs/adr/` 51개 전수).

### 2-2. PRD의 데스크톱 조항은 접근성 조항이다 (중요 — 초기 해석 정정)

`REQ-PWA-014`의 제목은 **"접근성·반응형 품질"**이고 본문 첫 문장은 **"핵심 과업은 모바일 우선이며 WCAG 2.2 AA 수준으로…"**다.

```
AC-PWA-014-01: 390px 모바일과 데스크톱에서 가로 스크롤 없이 핵심 플로우를 완료한다.
AC-PWA-014-02: 텍스트 200% 확대, 키보드, 명확한 포커스, 스크린리더 이름, reduced-motion…
AC-PWA-014-03: 공식성·권위·오류 상태를 색상이나 아이콘 하나만으로 구분하지 않는다.
```

즉 **데스크톱 "지원"은 요구되지만 데스크톱 "전용 정보구조"는 요구되지 않는다.** 승인 로드맵이 쓰는 단어도 일관되게 "반응형"이다 (`:390` "모바일 390px 기본, 데스크톱 반응형", `:416` "모바일 우선 그리드와 데스크톱·PWA standalone·safe-area 규칙").

### 2-3. 기기 분포 데이터가 0이고, 소급해서도 알 수 없다

- 서버가 User-Agent 를 읽는 곳 0 (`request.headers` 접근 4곳은 전부 request-id·CSRF·rate-limit IP)
- 프론트 텔레메트리 0 (GA/PostHog/Plausible/Amplitude/Mixpanel 전부 없음)
- DB 테이블 10개 전수에 device/viewport/browser/os 컬럼 0
- `research_sessions.client_fingerprint` 컬럼은 존재하나 **유일한 쓰기 지점이 하드코딩 `None`** (`apps/api/app/modules/chat/pipeline/stages/session.py:62`) → 한 번도 채워진 적 없음
- 체험단 33명(질문 518건 / 3주) 자유서술 결함 지적 40여 종 전부 콘텐츠 품질. **화면·기기·글씨 관련 1건도 없음**
- 그 체험단마저 **98%가 선문대 신학과 학생**. 보고서 자신이 "일반 식구·초신자·장년층 데이터는 0"이라고 명시

### 2-4. PC 시안의 핵심 기능은 프론트 문제가 아니라 백엔드 문제다

시안 4안이 공통 채택한 PC 레버 중 **P0-3(문장↔청크 각주 정렬)과 P0-4(호버 프리뷰)는 백엔드 API 확장이 선행돼야 한다.** 현재 `ChatSourcesEvent` 는 문장↔청크 매핑을 내려주지 않는다. 구현하려면 `assistant-message.tsx:36~76` 의 ReactMarkdown 파이프라인을 문장 단위로 쪼개고 청크 offset 과 정렬해야 한다 — **렌더러 재작성 + RAG 응답 스키마 확장**이다.

A안 설계자 본인의 평가: *"A안은 5.5 사람-일에 PC 레버 9개 중 2개를 준다. 나머지 7개 중 4개는 A안의 장점이 작동하지 않는 영역이다."*

> **이것이 이 결정의 진짜 규모다.** "PC 레이아웃을 만든다"가 아니라 "RAG 응답에 문장 단위 근거 매핑을 추가한다"가 비용의 본체다.

## 3. 탈락안과 그 이유

### B — 공유 훅 + 뷰 컴포넌트 2벌 (6점)

가장 "정석"처럼 보이지만 세 렌즈 모두 하위였다.

- **유지보수(2):** `useChatSession()` 추출 자체는 훌륭하다(358줄, stripDisclaimer 중복 해소, 이 레포 최초의 스트리밍 누적 단위 테스트). 그러나 뷰 2벌을 영구 확정하면서 **행동 동일성을 강제할 장치가 0개**다. 설계자 본인도 "쓰이지 않는 뷰는 조용히 썩는데, 썩는 것을 감지할 신호가 없다"고 인정했다
- **실행위험(2):** 뷰 경계(1152px) 리사이즈가 뷰 트리를 **언마운트·리마운트**한다. "훅이 살아남아 SSE 무중단"이라는 가정이 미검증. 또 계획대로 실행하면 **기존 E2E 5건이 깨지는데 설계가 그것을 인지하지 못했다** (`playwright.config.ts` 에 `viewport` 키가 없어 기본 1280×720에서 도는데, B의 경계가 1152라 전부 데스크톱 뷰를 밟는다)
- **제품전략(2):** 0건의 사용자 증거로 영구 이중 유지보수를 확정

### C — 라우트/엔트리 분리 (3점)

- 운영 중 서비스를 깨뜨릴 위험이 유일하게 **"레이아웃 파손"이 아니라 "진입점 파손"** 급
- 설계 전체가 `NextResponse.rewrite` × RSC 동작이라는 **미검증 가정**에 걸려 있고, fallback(2 URL + 307)은 C가 근거로 든 딥링크 보존을 무효화한다
- 미착수 M5(PWA)에 되돌릴 수 없는 선제 제약: `/desktop` 라우트가 `manifest.start_url`·서비스워커 precache에 물린다. 설계자 본인이 "설치된 앱의 캐시는 사용자 기기에 있어 배포로 100% 통제되지 않는다"고 인정

## 4. A와 D가 동률인 이유

**A(반응형 단일 뷰)** 는 *만드는 안 중 최선*이다. 유지보수 1위(뷰 1벌, 드리프트 구조적 차단), 배포 구조상 가장 깨끗(라우트 0 증가, `make deploy-web --no-deps` 만으로 끝남), 승인 로드맵이 이미 쓰는 "반응형" 기제와 정합.

**D(PC 보류·계측 우선)** 는 *안 만드는 안 중 최선*이자 실행위험·제품전략 1위다. 결정적 근거: **타이밍 민감 로직(SSE·AbortController·세션 하이드레이션)을 한 줄도 건드리지 않는 유일한 안**이다. 나머지 4안은 전부 `useChatSession` 360~400줄 추출을 전제하는데 —

> **`apps/web/src/test/` 10개 파일 중 `(chat)/page.tsx` 를 렌더하는 것이 0개다.** 안전망은 Playwright 6케이스뿐이고 그중 스트림·abort·오류 경로를 실제로 밟는 건 3개.

## 5. 권고 — 순차 조합

A와 D는 배타적이지 않다. **D로 시작해서 데이터가 말하면 A로 간다.**

### 단계 0 — 지금 당장 (어느 안으로 가든 순이익, 약 0.5일)

1. **기기 계측을 붙인다.** 이것 없이는 6개월 뒤에도 같은 질문을 데이터 없이 하게 된다
   - `research_sessions` 에 `device_class`(`mobile`|`tablet`|`desktop`) 파생 컬럼 1개. User-Agent 원문은 저장하지 않는다 (훈독 PRD `AC-PWA-015-01` 개인정보 원칙 준수)
   - `analytics_repository` 에 집계 쿼리 1개 + admin 대시보드에 분포 카드 1개
   - **주의:** 미사용 `client_fingerprint` 컬럼을 재활용하지 말고 새 컬럼을 쓴다. 의미가 다르다
2. ~~PC 시안 8개를 커밋한다~~ → **철회.** 사용자 결정으로 시안 HTML 9개는 폐기했고, 구조 요약([archive](../archive/design-2026-09-pc-chat/README.md))만 보존한다. 4안 전부 3-pane 이라 A안(모바일 골격 + breakpoint 분기)의 전제와 어긋난다

### 단계 1 — 안전망 먼저 (약 1일)

`(chat)/page.tsx` 를 렌더하는 테스트가 0개인 상태를 먼저 고친다. 스트리밍 누적 / abort / placeholder dedupe / 세션 하이드레이션 4경로. **이건 리팩터링의 전제조건이지 리팩터링이 아니다.**

### 단계 2 — 무조건 이득인 것만 (약 1.5일)

어느 안으로 가든 필요하고, 되돌릴 이유가 없는 것:
- `useChatSession()` 추출 (`page.tsx` 1217줄 → 도메인 로직 360~400줄 분리)
- `stripDisclaimer` 중복 제거 (`page.tsx:91` + `history/page.tsx:45` → `features/chat/`)
- dead code 정리 (`lib/reactions-api.ts` 참조 0건)

**단계 2는 "PC 뷰를 만든다"는 결정과 무관하다.** 1217줄 단일 컴포넌트는 그 자체로 부채다.

### 단계 3 — 데스크톱 하한 충족 (약 0.5일)

PRD 접근성 조항(`AC-PWA-014-01`)이 요구하는 수준만: 데스크톱에서 가로 스크롤 0, `max-w-2xl` 을 읽기 편한 폭으로 조정, 여백 정리. **정보구조는 건드리지 않는다.**

### 단계 4 — 4~8주 뒤 재판단

계측 데이터를 보고 결정한다:

| 관측 | 결정 |
|---|---|
| 데스크톱 세션 < 10% | D 유지. PC 시안은 보관. M5·콘텐츠 품질에 집중 |
| 데스크톱 세션 10~30% | A안 단계 3~4(근거 패널 + 세션 레일)만. 시안 4안 중 1개 채택 |
| 데스크톱 세션 > 30% | A안 전체 + P0-3/P0-4 백엔드 확장 검토 (§2-4의 진짜 비용) |

추가 판단 재료: 4050·6070+ 장년층과 교회장·교사 비중. 이들은 PC 친화적 과업(`docs/research/17-design-strategy.md:18` "전 연령 포용", `docs/prd/16-app-feature-spec.md:245` "큰 글씨 모드(장년층)")이 명문화된 대상층이다.

## 7. 미해결 질문

- `[확인 필요]` 데스크톱 breakpoint 임계값. 시안은 1280 기준이나 `playwright.config.ts` 에 `viewport` 키가 없어 기존 E2E 4개 프로젝트가 기본 1280×720에서 돈다. 임계를 1280에 두면 기존 E2E가 새 레이아웃을 밟는다. **제품 결정을 테스트 인프라 때문에 비틀지 않으려면 `viewport` 를 먼저 명시해야 한다**
- `[확인 필요]` `/history`(515줄)의 존치. 세션 레일이 목록을 상시 노출하면 `/history` 는 "검색·필터가 되는 레일" 이상이 아니게 된다. 단계 4 착수 전에 존치/흡수를 결정해야 한다
- `[확인 필요]` 훈독 PWA PRD 4개 경쟁안(PR #262~#265)이 미확정(`DEC-PWA-017`)이다. 정보구조가 서로 충돌하므로, 이것이 정해지기 전에 챗 화면 정보구조를 확정하면 나중에 충돌한다
